The shape of it

One idea holds the design together: the compiler in @elemnt/core is pure and runs in two places. The editor runs it in a Web Worker for the live preview, and the server runs it on every save. Both produce the same HTML (for people) and Markdown (for agents), so a preview bug and a published-page bug are almost always the same bug.

The editor's worker also runs @elemnt/core, so its preview matches what the server stores. Postgres holds only metadata and blob hashes; the page bodies live in the blob store.

How requests flow

Each flow lists the real call chain. When something breaks, find the flow, then walk it until the step that misbehaves.

1 · Typing in the editor → live preview

  1. CodeMirror changes source state. SourceEditor.tsx → PageEditor.tsx
  2. useCompiler(source) posts {id, source} to the worker; stale replies are dropped. useCompiler.ts
  3. Worker runs createElemnt().compile(source), the same function the server runs. compile.worker.ts
  4. Diagnostics go to the gutter; HTML goes to Preview, which registers widgets (POST /api/widgets/preview) and calls enhance(). Preview.tsx

2 · Save and publish

  1. 1.5 s after typing stops, or on Publish, the editor sends PUT /api/pages/:id with {source, baseRevisionId, publish}. Publishing an unchanged draft uses POST /api/pages/:id/publish instead. PageEditor.tsx save()
  2. Middleware resolves the viewer from Bearer token or cookie; pageWithAccess requires the editor role. 401 / 403 / 404 app.ts
  3. updatePage checks the edit lock 423 and that baseRevisionId is still the head 409. services/pages.ts
  4. compileAndStore: compile + widget scan. Errors block a publish but not a draft 422 with diagnostics. pages.ts → widgets.ts
  5. Writes three blobs (source, HTML, Markdown) keyed by sha256, then stores widget code.
  6. One transaction inserts the revision and moves draftRevisionId or publishedRevisionId, conditional on the head, so two concurrent saves can't both win 409.

3 · A reader opens a page

  1. GET /s/:space/:path. Private space without sign-in redirects to /login. app.ts, last route
  2. Picks the view: .md suffix or Accept: text/markdown → raw Markdown; ?view=markdown, ?view=present, ?level= are variants.
  3. Records a view (failures only log recordView failed), reads the stored HTML from the blob store. Nothing is compiled at read time.
  4. decorateWidgets, then renderShell wraps it with theme CSS, a CSP nonce, share and edit links. render/page.ts
  5. The browser loads /assets/elements.js and calls enhance(). If that bundle isn't built, pages still render, just static.

4 · ⌘I: Claude edits the page

  1. POST /api/pages/:id/assist with instruction, baseRevisionId and optional selection. Unsaved changes 409. app.ts
  2. aiClient picks the workspace key, else ANTHROPIC_API_KEY. None 400 "Claude isn't set up".
  3. anthropicProvider.json() streams a JSON-schema reply with the authoring guide as cached system prompt. services/ai.ts
  4. createSuggestion stores the proposed source as a blob. Nothing changes on the page yet. services/suggestions.ts
  5. Accept applies chosen hunks onto the current head; overlapping edits 409. The result is saved as a draft through updatePage.

5 · Claude Code over MCP

  1. Client calls /mcp; without a token it gets 401 and a WWW-Authenticate pointing at OAuth metadata. app.ts /mcp, services/oauth.ts
  2. handleMcp builds a fresh MCP server per request for that viewer. mcp.ts
  3. Tools: list_spaces list_pages search get_page get_authoring_guide get_style_guide validate get_runbook read; create_draft suggest_edit add_comment link_repo save_my_style write, only as drafts, suggestions or comments.
  4. Service errors return as tool errors with the message (and diagnostics) so the model can fix and retry.

6 · Widgets and runnable code

  1. The sandbox origin is the same server under a second hostname. The first middleware compares Host and hands the request to sandboxApp, which only answers /w/*. app.ts top, sandbox.ts
  2. Locally, localhost and 127.0.0.1 are used as the two origins automatically. In production you must set ELEMNT_SANDBOX_URL, or widgets and Run are off.

7 · Repo drift check

  1. GitHub push webhook → /integrations/github/webhook, signature checked with GITHUB_WEBHOOK_SECRET.
  2. For each linked page, checkDrift runs in the background; failures log drift check failed for … and never reach the user. services/repos.ts
  3. Proposed edits land as suggestions with origin drift; accepting one re-pins the page to the new commit.

Something broke: the routine

Step 1

Is it up?

curl localhost:8787/healthz. ok means the server reaches Postgres; 503 database unreachable means it doesn't.

Step 2

Read the server log

Any unexpected error is printed with its stack by onError, and the client only sees "Something went wrong on our side."

Step 3

Find the layer

Wrong output → core. Dead button → elements. Error JSON → server service. Blank editor → web console.

Step 4

Reproduce in a test

Copy the closest test, make it fail, then fix. Server tests need no Docker.

Call the API directly

Taking the browser out of the loop tells you quickly whether a bug is in the server or the client.

T=your_api_token
curl -s localhost:8787/api/me -H "Authorization: Bearer $T"
# Compile any source on the server and see diagnostics, without saving:
curl -s localhost:8787/api/preview -H "Authorization: Bearer $T" -H 'Content-Type: application/json' \
  -d '{"source":":::callout{type=warn}\nHi\n:::"}' | jq .diagnostics
# What an agent sees for a page:
curl -s localhost:8787/s/demo/tour.md
# Is Claude configured, and from where?
curl -s localhost:8787/api/ai -H "Authorization: Bearer $T"

Tests

Server tests run against an in-memory Postgres (PGlite) with migrations applied, an in-memory blob store and a fake Claude, so no Docker and no API key are needed. They also import core from source, so core changes don't need a rebuild.

pnpm test                                              # everything
pnpm --filter @elemnt/server test                      # one package
pnpm --filter @elemnt/server exec vitest run test/write-path.test.ts
pnpm --filter @elemnt/server exec vitest run -t "stale"   # by test name
pnpm --filter @elemnt/core exec vitest run -u           # accept intended snapshot changes
pnpm typecheck                                         # CI also runs this; build first

Looking at data

docker compose exec postgres psql -U elemnt
-- A page's state: which revision is live, which is a draft, who holds the lock
select id, path, published_revision_id, draft_revision_id, locked_by, locked_until from pages;
-- A page's history, newest first
select id, parent_revision_id, message, created_at from revisions where page_id = 'pg_…' order by created_at desc;
-- Open suggestions and where they came from (assist, mcp, drift, ask)
select id, origin, status, summary from suggestions where status = 'open';

Revision rows hold hashes, not text. To read a body from disk: cat cat data/blobs/<first two hex chars>/<hash>lt;ELEMNT_BLOB_DIRcat data/blobs/<first two hex chars>/<hash>gt;/cat data/blobs/<first two hex chars>/<hash>lt;first two hex charscat data/blobs/<first two hex chars>/<hash>gt;/cat data/blobs/<first two hex chars>/<hash>lt;hashcat data/blobs/<first two hex chars>/<hash>gt; (in Docker that is /data/blobs inside the server container). Or use GET /api/revisions/:rev/source (also html and markdown).

Ids carry their type as a prefix, so a stray id in a log tells you what it is: ws_ workspace, usr_ user, tok_ token, spc_ space, pg_ page, rev_ revision, sug_ suggestion, cmt_ comment, cmp_ library component, oac_ OAuth client, lip_ LinkedIn post, q_ reader question.
